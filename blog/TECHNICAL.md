# Scary Spider SEO Blog: Technical Details

This file is the deep-dive companion to `blog/CLAUDE.md`. It documents the
internals, invariants, and traps that are easy to break without knowing they
exist. Read it before touching auth, media, server actions, or anything that
runs on the edge.

Part of the `gseo` monorepo. Public-facing copy must never use em dashes
(see the root `CLAUDE.md`); this file is internal documentation.

---

## 1. High-level architecture

A single Next.js 15 App Router application that is compiled with OpenNext
(`@opennextjs/cloudflare`) and deployed as one Cloudflare Worker. There is no
separate API server, no node.js process, and no build-time database. Every
request, public or admin, runs inside `workerd`.

```
Browser
  │  HTML / JSON / server-action POSTs
  ▼
Cloudflare Worker  (blog.scaryspiderseo.com, custom domain)
  ├── ASSETS   → prebuilt static assets (.open-next/assets)
  ├── DB       → Cloudflare D1 (SQLite via Drizzle ORM)
  ├── MEDIA    → Cloudflare R2 (post images, served by /media/[key])
  └── SESSION_SECRET (secret, in Worker settings / .dev.vars)
```

Data flow notes:

- **Server actions, not a REST API.** All admin mutations and comment
  mutations are `"use server"` functions imported directly into client
  components. There is no `route.ts` for admin writes anywhere.
- **Event-driven? No.** Unlike the desktop app in `src/`, this project is
  request/response all the way. Do not build long-lived background state.
- **`getCloudflareContext` is the only way to reach bindings.** Always call it
  inside the function that needs bindings; never import bindings at module
  scope (they do not exist until a request is being handled).

## 2. Bindings, env, and the two type declarations

| Binding          | Kind     | Purpose                                   | Declared in                |
| ---------------- | -------- | ----------------------------------------- | -------------------------- |
| `DB`             | D1       | SQLite database via Drizzle               | `wrangler.jsonc`           |
| `MEDIA`          | R2       | Post cover/body images                    | `wrangler.jsonc`           |
| `ASSETS`         | Static   | Prebuilt Next.js assets                   | `wrangler.jsonc`           |
| `SESSION_SECRET` | Secret   | HMAC key for session cookies + IP hashing | `lib/cloudflare-env.d.ts`  |

There are **two** env type files and they must stay in sync:

- `cloudflare-env.d.ts` is generated by `npm run cf:typegen`
  (`wrangler types --env-interface CloudflareEnv cloudflare-env.d.ts`).
  It declares `DB`, `MEDIA`, `ASSETS` plus the entire workerd runtime types.
- `lib/cloudflare-env.d.ts` is hand-written and augments the generated
  `CloudflareEnv` interface with `SESSION_SECRET`. It exists because
  `SESSION_SECRET` is a secret, deliberately has no entry in `wrangler.jsonc`,
  and therefore is not produced by `wrangler types`.

`SESSION_SECRET` values: production lives in Worker settings
(`wrangler secret put SESSION_SECRET`), local dev in a gitignored
`.dev.vars` file (copy `.dev.vars.example`).

### Sync vs async context

`getCloudflareContext()` without options is synchronous and only works where
`waitUntil`/the current request context is available synchronously, notably
`middleware.ts`. Everywhere else (server actions, route handlers, server
components, `lib/db/client.ts`) use `getCloudflareContext({ async: true })`.
Mixing this up throws "Cloudflare context is not available".

## 3. Database

D1 via Drizzle (`lib/db/schema.ts`). All timestamp columns use
`mode: "timestamp"` (stored as integer epoch millis). No foreign-key
enforcement at runtime is relied on; D1/SQLite enforces the declared
references where possible.

Tables:

- **`posts`** — `slug` (unique), `title`, `excerpt`, `content` (HTML),
  `keyTakeaways` (JSON string[]; rendered as a highlighted bulleted box),
  `faqs` (JSON `{question, answer}[]`; rendered as Q&A plus FAQPage schema),
  `coverImageKey` (either `/media/<key>` or a hand-pasted external URL),
  `coverImageAlt`, `authorId` (FK to `users`, set null on user delete; shown
  as an author card and linked from `/author/<username>`), `category`
  (freeform text, not a FK), `metaTitle`,
  `metaDescription`, `status` (`draft`|`published`), `publishedAt`,
  `createdAt`, `updatedAt`. Both JSON sections are parsed defensively by
  `lib/post-sections.ts` (garbage/legacy values yield `[]`).
- **`categories`** — `slug` + `name` (both unique). This is a light list of
  suggestions, **not** a taxonomy: posts store their category as a freeform
  string, and renaming a category bulk-updates matching posts'
  `posts.category` (see `categories-actions.ts::renameCategory`).
- **`settings`** — key/value table. Currently `posts_per_page` and
  `comments_require_approval`. New settings should be added as helpers in
  `lib/db/settings.ts`, not ad hoc.
- **`users`** — `username` (unique), `passwordHash` (PBKDF2, format
  `<base64 salt>:<base64 hash>`, 100k iterations SHA-256), `role`
  (`admin`|`editor`), plus a public author profile: `displayName` (falls back
  to username in display), `avatarKey` (a `/media/<key>` path, like cover
  images), `jobTitle`, `bio`. Edited via `/admin/profile` (self) or the
  create-user form (admins).
- **`comments`** — `postId` (cascade delete), `userId` (nullable, set null;
  always null today, all commenters are anonymous), `authorName`, `content`,
  `ipHash` (HMAC'd IP, see section 9), `status`
  (`pending`|`approved`|`rejected`).
- **`comment_votes`** — `commentId` (cascade delete), `voterKey` (anonymous
  per-browser cookie id), `value` (1 or -1), unique on
  `(commentId, voterKey)`.

### Migrations

- Generate: `npm run db:generate` (drizzle-kit, schema → `migrations/`).
- Apply local: `npm run db:migrate:local` (`wrangler d1 migrations apply blog-db --local`).
- Apply remote: `npm run db:migrate:remote`.
- `drizzle.config.ts` needs no live credentials: migrations are applied by
  wrangler, not by the app.

## 4. Auth, sessions, and permissions

Hand-rolled, no auth library. Everything lives in `lib/auth.ts` and only uses
Web Crypto so it can run in Next's **edge runtime** (it is imported by
`middleware.ts`, which cannot resolve `node:crypto`). Note it still uses
`Buffer` (base64 helpers), which is why the Worker needs the
`nodejs_compat` compatibility flag.

- **Passwords.** PBKDF2-SHA256, 100,000 iterations, 16-byte random salt.
  Stored as `<salt b64>:<hash b64>`. Verify is constant-time
  (`constantTimeEqual`). Seeding/resetting a password uses
  `npm run admin:hash-password -- "your-password"`.
- **Sessions.** `createSessionCookieValue` signs `{ userId, username, role,
  exp }` (7-day TTL) as `base64url(payload).base64url(hmac)` using
  HMAC-SHA256 with `SESSION_SECRET`. The cookie is `httpOnly`, `secure`,
  `sameSite=lax`. `verifySessionCookieValue` checks the signature and expiry
  and never trusts the payload alone. This is a signed cookie, not a JWT
  library, and not server-side session storage.
- **Gating.** `middleware.ts` matches `/admin/:path*`, redirects unauthenticated
  users to `/admin/login`, and additionally bounces non-admins away from
  `/admin/users/*` and `/admin/settings`.
- **The one exception to middleware-gating.** `middleware.ts` only checks the
  session exists. Any *action* that is admin-only must re-check the role itself:
  `users-actions.ts` and `settings-actions.ts` call their own `requireAdmin()`
  (`lib/session.ts::getSession` + `role === "admin"`). `posts`, `categories`,
  and comment moderation deliberately trust the middleware gate, so editors
  can use them. If you add an admin-only action, follow the `requireAdmin()`
  pattern, do not rely on the route gate.

`lib/permissions.ts` defines the admin/editor matrix (`can(role, permission)`)
for finer-grained checks inside pages/actions. Admin: everything. Editor:
`posts:write`, `categories:write` only.

## 5. Admin CMS and server actions

Admin routes live under `app/admin/`, all behind the middleware gate and
`app/admin/layout.tsx` (which emits `robots: index:false, follow:false`).
State lives in React components (`useActionState`); there is no store layer.

Server action files (each `"use server"`):

| File                             | Mutations                                                |
| -------------------------------- | -------------------------------------------------------- |
| `app/admin/posts-actions.ts`     | `createPost`, `updatePost`, `deletePost` (+ R2 cleanup)  |
| `app/admin/media-actions.ts`     | `uploadImage`, `deleteMediaKeys`                         |
| `app/admin/categories-actions.ts`| `createCategory`, `renameCategory`, `deleteCategory`     |
| `app/admin/users-actions.ts`     | `createUser`, `updateUserRole`, `deleteUser` (admin-only)|
| `app/admin/settings-actions.ts`  | `updateSettings` (admin-only)                            |
| `app/admin/comments-actions.ts`  | `approveComment`, `rejectComment`, `deleteComment`       |
| `app/admin/login/actions.ts`     | `login`, `logout`                                        |
| `app/comments-actions.ts`        | `submitComment`, `voteComment` (public)                 |

### The critical trap: server action body size

Next.js server actions default to a **1 MB request body limit**. Image uploads
travel as multipart `FormData` inside a server action, so anything over 1 MB
was rejected with a 413 before `uploadImage` even ran, leaving the UI stuck
on "Uploading...". `next.config.ts` now sets
`experimental.serverActions.bodySizeLimit: "10mb"` (nested under
`experimental` for this Next version; top-level `serverActions` is rejected as
an unrecognized key), comfortably above the 8 MB `MAX_BYTES` ceiling in
`media-actions.ts`. If you ever raise `MAX_BYTES`, raise `bodySizeLimit` to
match.

Client callers wrap `uploadImage` in `try/catch/finally` so a network or
server failure surfaces as a visible error instead of an infinite spinner.

## 6. Media pipeline (R2 + WebP)

Uploads (cover image and inline body images) go through the same server
action, `uploadImage` in `app/admin/media-actions.ts`:

1. Client converts the file to WebP (see below) and posts it as FormData.
2. Server validates `file instanceof File`, allowlisted MIME
   (`png/jpeg/webp/gif/avif`), and `<= 8 MB`.
3. Key is `crypto.randomUUID() + "." + file.type.split("/")[1]` (always
   `webp` after conversion, or the original ext for GIF/AVIF passthrough).
4. `env.MEDIA.put(key, bytes, { httpMetadata: { contentType }, customMetadata: { name: file.name } })`.
5. Returns `{ url: "/media/<key>" }`.

The UUID key is the id; the human-readable `name` (the uploaded file name,
e.g. `<base>.webp`) is stored as R2 `customMetadata` and surfaced by the media
library.

Serving: `app/media/[key]/route.ts` streams the R2 object with
`Cache-Control: public, max-age=31536000, immutable` and the object's ETag.
Keys are content-addressed (random UUID), so immutable caching is safe.

### WebP conversion (client-side, on purpose)

`lib/webp.ts::fileToWebP` re-encodes JPEG/PNG to WebP **in the browser**
using `createImageBitmap` + `canvas.toBlob("image/webp")` (quality 0.82)
*before* the bytes are uploaded. Rationale: WebP encoding needs a native
codec, and Cloudflare Workers cannot run one without bundling a large WASM
binary. The browser already has a codec, so the admin page does the work and
R2 only ever stores compact WebP files.

Rules encoded in `lib/webp.ts`:

- **GIF passes through untouched** to preserve animation (canvas can only
  draw the first frame).
- **AVIF passes through** (already a modern, compact format).
- If conversion throws for any reason, the original file is uploaded rather
  than failing the upload.
- The resulting `File` is named `<basename>.webp` with `type: image/webp`, so
  the server stores it with a `webp` extension and content type.
- `PostForm.tsx` converts the cover image right before upload;
  `RichTextEditor.tsx` converts at file-selection time so the preview blob is
  the same WebP that will be inserted.

### Deferred uploads for in-post images

Images added to the post body are **not** uploaded when inserted. The editor
inserts a local `blob:` URL (with the file kept in `lib/pending-images.ts`
`PendingImage` entries) and only uploads them all to R2 when the post is saved
(`PostForm` intercepts `onSubmit`, runs `resolvePendingImageUploads`, rewrites
every `blob:` src to `/media/<key>`, then lets the form's server action
proceed via `requestSubmit`). The cover image is the exception: it still
uploads immediately on click (its URL is just a text field).

Un-uploaded images are listed under the editor ("Not uploaded yet") with
click-to-preview (a modal), Change (re-select file, rewrites the `<img>` node
src via a doc transaction), and Remove (deletes the matching `<img>` node).
Blob URLs are tracked and revoked on unmount. The submit interception is a
two-pass dance: the first `onSubmit` prevents default, uploads, writes the
final HTML into the (uncontrolled) hidden `content` field, then calls
`requestSubmit()` while a ref flag lets the second submit pass through to the
native form action. Do not "simplify" this into calling the `useActionState`
dispatch with a hand-built FormData: React warns that `isPending` will not
update correctly outside a transition.

### Media library and reuse

`/admin/media` (server page + `MediaGallery.tsx`) lists every uploaded image
via `listMediaImages` (R2 `list`, filtered to image extensions, sorted
newest-first), with click-to-preview, Copy URL, Delete, and Load more.
Deletes go through `deleteMediaImage`, which refuses to remove any key still
referenced by a post (checked against `posts.content` and `coverImageKey`).
The editor's "from library" button (`MediaPicker.tsx`) reuses the same list
to insert an existing `/media/<key>` directly into the post body.

### Referenced-key tracking and orphan cleanup

`lib/media.ts` extracts media keys from stored HTML: any `/media/<key>` inside
`content`, plus the `coverImageKey` field (which may also be an external URL,
in which case it is skipped). On `updatePost`/`deletePost`,
`posts-actions.ts` diffs old vs new keys (`diffRemovedMediaKeys`) and calls
`deleteMediaKeys` (best-effort; a failed R2 delete never blocks the save).

**Trap:** the regex only matches keys like `<uuid>.<ext>` (alphanumeric,
dash, dot). If a future upload format changes the key shape, update
`MEDIA_SRC_PATTERN`/`BARE_KEY_PATTERN` or orphaned objects will accumulate.

## 7. Public rendering and SEO

Public pages query D1 on the Worker. `app/page.tsx`, `app/[category]/[slug]/page.tsx`,
`app/[slug]/page.tsx`, and `app/author/[username]/page.tsx` set
`export const revalidate = 3600` (ISR-style caching with OpenNext), while
`sitemap.ts` and `feed.xml/route.ts` are `force-dynamic` because a fresh
clone/CI/local D1 has no tables yet and prerendering at build time would fail.

- **Post URL scheme.** Posts live at `/<category-slug>/<slug>` when they have
  a category (slug derived from the freeform name by `lib/post-url.ts`, not a
  DB column), and stay at `/<slug>` when uncategorized. The legacy flat route
  `app/[slug]/page.tsx` `permanentRedirect`s categorized posts to their
  canonical `/<category>/<slug>` path, and the `[category]` segment is
  validated on the canonical route too, so one URL per post stays in the index.
  Every URL producer (`sitemap.ts`, `feed.xml`, JSON-LD, `PostCard`,
  `BlogSidebar`, comment moderation) goes through `postPath`/`postUrl`; never
  hard-code `/${post.slug}`.

- **Canonical trap on the home page.** Next's metadata resolver drops the
  query string when the canonical *path* is `/` (it collapses to the bare
  origin). So `/?category=...` / `/?page=2` canonicals are emitted as a manual
  `<link rel="canonical">` in the page body (React 19 hoists it into `<head>`).
  `generateMetadata` only returns `alternates.canonical: "/"` when there is no
  query string. Do not "simplify" this; the manual link is deliberate.
- **Search-result pages are noindex.** Any `/?q=` page returns
  `robots: { index: false, follow: true }` to avoid thin near-duplicate
  "site search" pages.
- **Metadata is not merged.** Next does not deep-merge nested `openGraph`
  objects between the root layout and a post page, so
  `generateMetadata` in `[slug]/page.tsx` re-specifies everything, including a
  fallback `og-image.png` when a post has no cover.
- **JSON-LD.** `Blog` on the home page, `BlogPosting` on post pages
  (`app/page.tsx`, `app/[category]/[slug]/page.tsx` via `PostPageView`). When a
  post has an author, the `BlogPosting` author is the `Person` (linking to the
  author page); otherwise it falls back to the site `Organization`.
- **Authors.** Each user has a public profile at `/author/<username>`
  (`app/author/[username]/page.tsx`) listing their published posts. Post pages
  render an `AuthorCard` under the article when `posts.authorId` is set.
- **Key takeaways / FAQs.** `PostArticle` renders `posts.keyTakeaways` as a
  highlighted bulleted box above the body and `posts.faqs` as a Q&A section
  below it. When FAQs exist, `PostPageView` also emits a separate `FAQPage`
  JSON-LD script alongside the `BlogPosting` one. Both sections are edited in
  `PostForm.tsx` (takeaways as one-per-line text, FAQs as a dynamic list).
- **sitemap.xml / robots.ts / feed.xml.** Sitemap lists `SITE_URL`, all
  published posts (canonical URLs), and author pages for users who have
  published posts; robots allows `/` and disallows `/admin`; feed.xml is
  RSS 2.0 with escaped XML, capped at 50 items, cached 1 hour. All use
  `lib/site.ts` URLs (`blog.scaryspiderseo.com`, main site
  `www.scaryspiderseo.com`).
- **Headings/TOC.** Body headings start at H2 (the `<h1>` is always the post
  title; see the Tiptap config in `components/RichTextEditor.tsx`).
  `lib/toc.ts::parseHeadings` injects stable `id` anchors (slugified, de-
  duplicated with `-2`, `-3`...), strips diacritics, and feeds
  `components/TableOfContents.tsx`.
- **SEO guardrails in the editor.** `lib/seo-limits.ts` deliberately mirrors
  the desktop crawler's thresholds in `src/lib/filters.ts`
  (`TITLE_MIN_LENGTH` 30 / `TITLE_MAX_LENGTH` 60, meta description ~155,
  thin content under 300 words) so a post that looks good in the admin form
  also passes a Scary Spider SEO crawl. These are advisory, non-blocking
  warnings in `PostForm.tsx`.

## 8. Content editing

`components/RichTextEditor.tsx` is a Tiptap editor (client component). It does
**not** render a form field itself: it reports the current HTML upward via
`onChangeHTML`, and `PostForm.tsx` mirrors that into an uncontrolled
`<input type="hidden" name="content">` (via a ref) so the submit handler can
rewrite it after uploading pending images. Do not move the hidden field back
into the editor: an uncontrolled input whose DOM value is mutated directly gets
remounted (and reset to its initial value) whenever a conditional sibling above
it toggles, which silently drops the submitted content and surfaces as "Slug,
title, and content are required." on save.

`PostForm.tsx` also tracks a `dirty` flag (any field change, editor edit, or
cover upload) and arms `lib/use-unsaved-changes.ts`, which warns on tab
close/reload (`beforeunload`), in-app link clicks (capture-phase anchor
interception + `window.confirm`), and browser back/forward (`popstate`). It is
deliberately disabled while a save/pre-upload is in flight so the redirect
never prompts, and it does not monkey-patch `history.pushState` (Next's
app-router owns that).

Extensions: StarterKit (headings restricted to 2-6, underline included),
link (autolink, openOnClick off), image, placeholder, table (resizable), plus
`TextStyle` and `FontSize` from `@tiptap/extension-text-style` (font size
select in the toolbar; commands `setFontSize`/`unsetFontSize`).

The toolbar is reactive: it subscribes through `useEditorState`, because in
`@tiptap/react` v3 `useEditor` has `shouldRerenderOnTransaction: false` by
default and would otherwise never light up the active formatting (bold/italic/
underline/lists/font size/undo) of the current selection. The image button
converts the picked file to WebP via `fileToWebP`, previews it, and inserts it
as a deferred blob image (see the media section for how those upload on save).

## 9. Comments, anti-spam, and voting

All commenters are anonymous today; `userId` is always null.

`app/comments-actions.ts::submitComment` defense layers:

1. **Honeypot.** A `website` field real users never see; bots that autofill it
   are silently "accepted" (success returned, nothing inserted).
2. **Time trap.** The form stamps `formStartedAt` at render; submissions in
   under 2 s are rejected.
3. **Rate limit.** `getRequestIpHash` (`lib/anti-spam.ts`) HMACs the client IP
   (`cf-connecting-ip` from Cloudflare, falling back to `x-forwarded-for` for
   local dev) with `SESSION_SECRET`, producing a one-way hash stored on the
   comment. Max 3 comments per 10 minutes per IP hash. This deliberately never
   persists a raw, reversible IP.
4. **Content checks.** Name <= 60 chars, comment <= 3000 chars, post must exist.

Approval is gated by the `comments_require_approval` setting: pending comments
appear in `/admin/comments` moderation (`approveComment`/`rejectComment`/
`deleteComment`), each revalidating the affected post. On the public side
`getPostComments` only selects `approved`.

`voteComment` dedupes by `voterKey` (the `voter_id` cookie, see below).
Clicking the same direction again retracts the vote; switching direction
updates it. Unique index on `(commentId, voterKey)` makes one vote per
comment per browser.

### Cookie mutation rules (`lib/voter.ts`)

`cookies()` can only be **written** inside a Server Action or Route Handler.
During a normal page render it is read-only. So:

- Pages that only need "has this visitor voted" call `getVoterKey()` (read).
- `voteComment` (a Server Action) calls `getOrCreateVoterKey()`, which mints
  the `voter_id` cookie on first use (1-year TTL).

Forgetting this throws "Cookies can only be modified in a Server Action or
Route Handler" when you try to set the cookie during a render.

## 10. Monorepo and CI integration

- This project is **not** in the root CI workflow (`.github/workflows/ci.yml`).
  Deploys are manual via `npm run cf:*` scripts. Directory-based path gating in
  CI means a `blog/`-only change skips desktop-app jobs and vice versa.
- `npm run cf:deploy` = `opennextjs-cloudflare build && opennextjs-cloudflare deploy`.
- Before first deploy: `wrangler r2 bucket create blog-media`, `wrangler d1
  create blog-db` (paste the returned id into `wrangler.jsonc` and `.dev.vars`),
  `wrangler d1 migrations apply blog-db --remote`, and
  `wrangler secret put SESSION_SECRET`.

## 12. Common traps checklist

- Raising `MAX_BYTES` in `media-actions.ts` without raising
  `serverActions.bodySizeLimit` in `next.config.ts` → 413s on upload.
- Using `getCloudflareContext()` (sync) in a server action instead of
  `{ async: true }` → "Cloudflare context is not available".
- Adding `node:` imports to a module imported by `middleware.ts` → edge-runtime
  build error.
- Writing a cookie during a page render → runtime error (must be a server
  action).
- Trusting the middleware gate for an admin-only *action* → privilege
  escalation; use `requireAdmin()`.
- Changing media key shape without updating `lib/media.ts` regexes → orphaned
  R2 objects.
- Rendering the post content hidden field inside `RichTextEditor` instead of
  `PostForm` → content silently dropped on save (uncontrolled-input remount).
- Moving in-post images back to immediate upload → the editor's pending-image
  list ("Not uploaded yet"), change/preview controls, and save-time batch
  upload in `lib/pending-images.ts` all depend on the deferred flow.
- Expecting the toolbar to update without `useEditorState` → active formatting
  never lights up (`useEditor` v3 does not re-render on transactions by
  default).
- Importing Cloudflare bindings at module scope → undefined at runtime.
- Sending GIFs through WebP conversion → lost animation (`lib/webp.ts`
  already skips them; keep it that way).
