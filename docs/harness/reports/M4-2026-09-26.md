### T4.2 Incremental Overview counts (ADR-0024)
Verifier acceptance:
- `IssueCounter` ingests each page once. Cross-page counts are recomputed at most once a second while the crawl runs, and exactly once it is paused, finished or loaded.
- Every one of the 91 `ISSUE_DEFS` entries now has a `crossPage` flag; 17 are true.
- A Proxy test proves page-local checks never read the filter context. The verifier flipped one flag on purpose and the tests caught it.
- The derived-state memo no longer copies tracker Sets or Maps.
- Tests `matches countIssues after incremental ingestion` (every issue key, after every batch), `ingests each page once`, `recomputes cross-page counts on finish`, and `50k pages in 100 page batches stays under 2 s total`.
- Measured with the 50k test's setup: about 178 s of CPU time before, about 1.9 s after.

Review round 1:
- Major: the "finish" test did not exercise the real change from live to finished. Fixed, and the replaced-array and stalled-crawl cases got their own tests.
- Minor: after a skipped recount, a stalled crawl never refreshed its cross-page counts. A trailing timer now caps the lag at about 1 s.

Known limits (recorded in ADR-0024):
- One cross-page recount costs O(pages x 17).
- With 150 ms flushes, a 50k-page crawl spends about 11 s of CPU on cross-page recounts. The follow-up is to make the duplicate and URL-set counts incremental.

Staging had already taken ADR-0023 (T4.6), so this task's ADR was renamed to ADR-0024.

### T4.3 Throttle progress events
Verifier acceptance:
- `ProgressThrottle` limits progress to one event per 100 ms, with a trailing emit for any update it held back.
- A forced emit is sent when pause changes, and one final forced emit before `crawl://done` on every exit after the loop.
- Frontend: progress is applied in the same batched flush as pages.
- Tests:
  - Throttle unit tests: `progress_throttle_limits_rate`, `progress_throttle_forces_through`, `progress_throttle_sends_swallowed_update_within_one_interval`.
  - Event count: `progress_events_are_throttled`. On the 30-page fixture crawl, 35 events unthrottled become 2 throttled.
  - Pause, resume and list-mode final-progress tests.

Review round 1 majors, both fixed:
- The throttle only emitted on the leading edge, so the UI could show stale counts for seconds.
- A buffered progress event could undo an optimistic Pause or Resume.

Minor findings (not fixed):
- An event the backend emits during the click's round trip can still show the old pause state briefly. The next forced emit corrects it.
- No fixture test drives the loop's trailing-emit branch.
- The hook change has no automated test, because the repo has no React hook test setup.

### T4.4 Stream saved crawls
Verifier acceptance:
- `snapshot.rs` writes compact JSON through a `BufWriter` into a hidden, uniquely named temp file next to the target. It calls `sync_all`, then renames over the target.
- A failed save leaves the old file byte for byte unchanged.
- `to_string_pretty` no longer appears anywhere in the source.
- Old pretty-printed saves still load.
- Tests `save_then_load_round_trips`, `loads_a_pretty_printed_legacy_file`, `failed_save_keeps_the_previous_file`, `compact_output_is_smaller_than_pretty`, and 7 busy-flag tests.

Review findings, all fixed:
- Round 1, major: saving mid-crawl held the crawl's locks through the disk write. It now clones when a crawl is running and streams directly when idle.
- Round 1, minor: save and load now run off the UI thread, and the temp file name is unique.
- Round 2, major: making load asynchronous let Start race with a load. Start, load and an idle streaming save now share a single atomic busy claim on `AppState::running`.
- Round 2, minor: `apply_snapshot` now holds the pages lock until the resources have been replaced.

Minor findings (not fixed):
- Clicking Start while a large idle save is still writing now shows a "try again" toast instead of waiting.
- If `run_crawl` panics, `running` is never cleared. This was already the case before.

## Decisions for you

1. **Perf test headroom.** The T4.2 50k test ran in 1937 and 1984 ms on a quiet machine, against a 2000 ms budget. Together with the existing flaky 20k tests (see the M3 report), wall-clock-style budgets are the main source of gate flakes. Options:
   - Raise the 50k budget, for example to 4 s.
   - Run the perf tests in a separate serial Vitest project or gate step.
   - Replace the absolute budgets with scaling checks.
2. **Lint and Vitest scan `.claude/worktrees/`.** Parallel worktree runs made `eslint .` crash on files that were changing underneath it, and made Vitest run duplicate test copies. Adding `.claude/worktrees/**` to the ESLint ignores and the Vitest `exclude` would fix it. That is a gate config change, so it is left to you.
