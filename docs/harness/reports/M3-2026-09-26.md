## Per task evidence

### T3.1 Include and exclude URL patterns (ADR-0015)
Verifier acceptance:
- scope.rs: `empty_scope_allows_everything`, `include_requires_a_match`, `exclude_wins_over_include`, `invalid_pattern_reports_its_index` (also rejects a pattern over the 1 MiB compiled size limit), `fragment_is_ignored_when_matching`.
- Fixtures: `exclude_pattern_skips_matching_pages` (excluded URLs still count as linked, for orphan detection), `include_pattern_limits_the_crawl`, `include_pattern_applies_to_sitemap_urls`, `resumed_crawl_drops_queued_urls_the_new_scope_excludes`.
- `start_crawl` rejects a bad pattern before touching any state.

Plan deviation: the include test uses `/noindex\.html$` instead of `noindex`, because a fixture added after the plan also matches the bare word.

Review round 1 majors, both fixed:
- A start rejected for a bad pattern wiped the table, and a following resume then showed only new pages. The previous view is now restored.
- A resumed crawl did not re-filter its queue with changed patterns. It does now.

Minor findings (not fixed):
- No test proves that dropping queued URLs frees their `max_pages` slots.
- Redirect targets are not checked against the patterns.
- The App.tsx restore path has no automated test, because the repo has no DOM testing library.

### T3.2 List mode (ADR-0016)
Verifier acceptance:
- `parseUrlList trims, dedupes and rejects non-http lines`.
- `list_mode_crawls_only_the_listed_urls` (depth 0, no sitemap, no link following).
- `list_mode_respects_robots_per_host`, which now uses a different robots.txt per origin so it really proves the rules are per host.
- `list_mode_fetches_robots_off_the_dispatch_path`, which uses a gated origin and a dead origin.
- Cap of 50,000 URLs, resume never used or stored in list mode.

Verification round 1 failed: the per-host robots test did not tell per-host from start-only rules.

Review round 1 findings, all fixed:
- Major: robots.txt was fetched serially inside the dispatch loop, so a multi-origin list crawled about one URL per robots round trip. It is now a per-origin `OnceCell` resolved inside the page tasks.
- A list start overwrote the Spider URL box. The results on screen are now tracked separately in `shownSource`.
- `paginationTargetError` flagged every paginated page in a list crawl.
- Include/exclude pattern fields looked active in list mode. They are now disabled with a note.

Trade-offs recorded in the ADR:
- Listed URLs ignore include/exclude patterns and `max_pages`.
- Lines without a scheme are rejected.
- Crawl-delay does not apply to an origin's first URLs until its robots.txt resolves.
- A reopened saved list crawl is treated as a spider crawl, so the pagination flags come back.

The dead-origin test adds about 4 s to `cargo test` on Windows.

### T3.3 Custom search (ADR-0017)
Verifier acceptance:
- `counts_literal_matches_case_insensitively`, `regex_rules_match`, `text_scope_ignores_markup_and_scripts`.
- Fixture `custom_search_counts`, filters test `custom contains and missing filters`.
- Rules are validated before the crawl: at most 10, with a 1 MiB regex size limit.
- Custom search is informational: it has its own Overview group and is not counted as an issue.

Review round 1 majors, both fixed:
- A reopened crawl took rule names from the current options sheet, so tiles could show another rule's name. Rules are now saved in `CrawlSnapshot.custom_searches`.
- Rule ids were reused, so a resumed crawl could mix two different rules in one column. Ids are now random (`cs-xxxxxxxx`), and a rule edited before continuing gets a new id.

Also fixed in round 1: parsing and matching now run in `spawn_blocking`, and CSV headers use the rule name.

Minor finding (not fixed): two rules with the same name produce duplicate CSV headers. T3.4 deduplicates extraction headers but not these.

### T3.5 Crawl comparison (ADR-0019)
Verifier acceptance:

- A Compare tab whose diff runs in a Web Worker and is O(n) using maps.

Review round 1 majors, both fixed:

Minor findings (not fixed):

### T3.6 Raw vs rendered HTML (ADR-0020)
Verifier acceptance:
- Keys `jsChangesTitle`, `jsChangesCanonical`, `jsChangesRobots`, `jsAddsMostContent` (raw words under half of rendered) and `jsAddsLinks` (more than 5 extra internal links after rendering), with solutions.
- "Compare raw and rendered HTML" option, which requires JS rendering.
- `raw_signals_copy_parsed_fields`, `compare_raw_html_without_rendering_records_nothing`, `rendered_same_document_ignores_only_the_fragment`.
- `js_rendering_changes_are_captured` is `#[ignore]` and passed with local Chrome.

Review round 1 findings, all fixed:
- Major: adding `index, follow` with JavaScript was flagged as a robots change. No-op directives are now ignored.
- A client-side navigation was blamed on JavaScript changes. Raw signals are now dropped when Chrome ends on a different URL.
- Raw values were not shown anywhere. They now appear in the page detail.
- A README row was wrong.

Minor findings (not fixed):
- A router that rewrites the URL on load (trailing slash, `?lang=`) silently loses the comparison. This errs toward reporting nothing rather than false issues.
- A raw `none` against a rendered `noindex, nofollow` counts as a change.
- No table or CSV columns for the raw values.

## Decisions for you

- **Perf test flakiness.** Measuring CPU time and retrying fixed most failures. The 500 ms test still fails when another build keeps the machine saturated for more than 30 s. Options, each outside what the harness may change on its own:
  1. Run the perf tests in their own serial Vitest project or gate step.
  2. Calibrate the budget against a reference workload timed in the same window.
  3. Replace the absolute budget with a scaling check, for example 20k pages against 2k.
  4. Keep it as is.
